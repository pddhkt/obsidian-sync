## 1)Multi-user + Role-based Access Control(RBAC)

**答案:做到,而且呢部分已經 design 入後台架構,屬而家報價範圍,唔額外收費。**

### 而家後台已經支援嘅角色架構

後台一開始已經以 multi-user + 權限分層去設計 —— 即係話**唔需要再額外開發**,只需要按 Imarflex 實際同事分工 set 起 roles。預設我哋會 ship 以下幾個常用 role(可以按需要再加 / 改名 / 微調):

| Role            | 典型同事           | 可以做                                                | 唔可以做                          |
| --------------- | -------------- | -------------------------------------------------- | ----------------------------- |
| **Super Admin** | 老闆 / IT 主管     | 全部 —— 包括加 user、改 role、睇所有報表、改網站設定                  | —                             |
| **Manager**     | 部門主管           | 大部分 —— 改產品、價錢、推廣、睇所有訂單同數據                          | 唔可以加 user / 改其他人嘅 role        |
| **Operations**  | 訂單 / 客服同事      | 睇訂單、改訂單狀態、做退換、處理客戶資料、回覆 inquiry                    | **唔可以改價錢、唔可以改產品 spec、唔可以發 promo** |
| **Marketing**   | Marketing 同事   | 寫 blog、改 banner、出活動 landing page、整 promo code、睇報表 | **唔可以改產品 spec、唔可以改訂單**        |
| **Content**     | Copywriter / 兼職 | 寫 blog、提交草稿                                        | 唔可以 publish(需 Marketing approve)、唔可以掂訂單 / 產品 |
| **Viewer**      | 老闆睇 dashboard / 投資者 | 淨係睇,唔改任何嘢                                          | 唔可以改任何嘢                       |

### Derek 提出嘅兩個例子 —— 直接 map

- **「客服得睇訂單但唔可以改價」** → **Operations** role:可以睇 / 改訂單狀態、處理退換,但見唔到「改產品價錢」呢個 button。
- **「Marketing 可以寫 blog 但唔可以改產品 spec」** → **Marketing** role:Blog / banner / promo 全部開放,但入到產品頁就係 read-only,改唔到 spec。

### 仲有嘅後備機制

- **Audit log(操作紀錄)** —— 每個 user 改咗咩、邊個訂單、邊個產品、幾時改 —— 全部有 log,出咗事可以追返。
- **二人 approve(可選)** —— 例如「改完價要 Manager approve 先 effective」,可以喺敏感欄位(價、退款超過某數)set,Imarflex 唔想要就唔開。
- **Session 管理** —— 同事離職可以即刻 revoke,佢登入緊個 session 即時 kick 走。
- **2FA(雙重認證)** —— Super Admin 同 Manager 強制開啟,Operations / Marketing 可選但建議開。

### Imarflex 需要做嘅嘢

開始嘅時候,話低 Imarflex 而家有幾多同事、邊個負責邊樣,我哋一齊 map 落上面嘅 roles(或者加新 role)。**呢個 setup 過程我哋包**,Admin training 嗰節順手做埋。

## 2)PDF 說明書 / 保養手冊管理 + PDP 顯示

**答案:做到,屬而家報價範圍。** 後台已預留**檔案管理(File Manager)**呢個模組,Imarflex 可以自助上載、命名、版本管理,然後一鍵 link 落 PDP。

### 後台會點操作

1. **檔案管理頁** —— 上載 PDF(亦支援 manual JPG / 影片 link),自動歸類「說明書 / 保養 / 食譜 / 其他」。
2. **每個檔案有 metadata**:檔案標題(中 / 英)、版本號(v1.0 / v2.1)、上載日期、適用產品(可 link 多個 SKU)。
3. **入到產品頁編輯** —— 「Downloads」section 揀要顯示邊幾個檔案、用咩 label(例如「電子版說明書」、「保養手冊」、「食譜」)。
4. **舊版本自動 archive** —— 上載新版說明書唔會 overwrite 舊版,舊版仍然可以追溯(例如舊型號客戶仲要用舊 manual)。

### PDP 客戶端體驗

每個產品頁會有一個「**下載 / Downloads**」section,顯示:

| 顯示內容 | 例子                                       |
| ---- | ---------------------------------------- |
| 檔案名  | 「IRC-20IH 電子版說明書」                        |
| 圖示   | PDF icon                                 |
| 大小   | 2.4 MB                                   |
| 動作   | 「下載」按鈕(直接 download,唔會跳走網頁)               |
| 語言版本 | 中文 / 英文分開列(如有),或同一檔案內雙語                  |

> 客戶體驗:落到 PDP 滑落「下載」section,睇到呢部產品有幾個 PDF 可以拎,一 click 即下載,唔需登入、唔需留 email(除非 Imarflex 想 gate 住做 lead capture —— 呢個都可以,睇下面)。

### 多咗嘅 bonus(已包,唔額外收)

- **客戶下載追蹤** —— PostHog 會 log 邊個產品嘅 manual download 最多,幫 Imarflex 睇邊類產品客戶最需要支援 / 邊本說明書最值得優化。
- **可選 Lead capture mode** —— 若 Imarflex 想,部分 PDF(例如食譜書、選購指南)可以 set「填 email 先下載」,自動入會員 list。預設**唔開**,Imarflex 想試先開,免得對保養手冊呢類「客戶已經買咗」嘅情況造成阻力。
- **Sitemap + SEO** —— PDF 會自動加入 sitemap,Google 搵到,部分 long-tail SEO 流量(例如「IRC-20IH 說明書 PDF」)會直接 land 落 PDP,順手帶 traffic。
- **OCR 數碼化(屬全包 retainer)** —— 如果 Imarflex 手上有紙本舊說明書 / 保養卡未 digitise,3.1 retainer 嘅 OCR 服務可以幫手轉做可搜尋 PDF。

### 技術細節(俾 IT 同事參考)

- 儲存喺 **Cloudflare R2**(同產品圖同一個 storage),免費額度足夠 Imarflex 規模。
- 每個檔案有 public URL,可以直接俾客服 email 比客人,或者印 QR code 落實體保養卡。
- 檔案大小建議 single PDF < 20 MB(大過就建議拆),系統技術上 200 MB 都頂得住。

## 3)Cross-border 擴展澳門 —— Multi-currency / 地址 / 運費

**答案:技術上做到,而且係我哋自建 platform 嘅一個明顯優勢(Shopline 呢方面有平台框架限制)。但建議分階段做,因為涉及嘅唔淨係技術,仲有稅務、物流、客服語言 / 時段。**

呢部分**屬未來擴展**(中長期 roadmap),唔屬而家報價範圍 —— 但因為我哋 platform 由零自建,可以**而家先預留架構**,將來 activate 嗰陣唔使大改。下面講清楚而家做幾多、將來做幾多。

### 而家(Phase 1,首階段上線)—— 已包

- **資料模型預留 multi-region 欄位** —— 產品有「適用地區」flag、價格有「貨幣 / 地區」維度、訂單記低 currency code。**而家全部 default 香港**,但 schema 已經支援將來開澳門。
- **地址欄位用 region-aware 格式** —— 而家用香港格式(區 / 大廈 / 樓 / 室),但底層係 flexible,將來開澳門時新增澳門格式(堂區 / 街道 / 大廈 / 樓)只需 config,唔使重寫。
- **網站可加 EN / 繁中(澳門大部分都睇繁中,但部分情境英文有用)** —— i18n 框架已 build,將來加語言 / 加地區嘅切換不再係大工程。

### 將來(Phase 2,正式擴展澳門)—— 另作報價

當 Imarflex 真係要正式對澳門賣嘢嗰陣,要做嘅嘢:

| 項目 | 內容 |
| ---- | ---- |
| **Multi-currency** | 加 MOP(澳門幣)顯示;客戶睇到 MOP 標價,結帳轉返 HKD / MOP 收(視乎支付商支援)。Airwallex 支援多幣結算,呢部分對接 OK。 |
| **地區切換** | 網站 header 加「香港 / 澳門」切換,記住客戶選擇。產品 catalog、價錢、運費按地區顯示。 |
| **運費邏輯** | 後台可 set per-region 運費規則(澳門可能要分平郵 / 速遞 / 滿額免運;海運 vs 跨境陸運)。 |
| **稅 / 報關** | 港澳跨境涉及 CEPA 同澳門入口安排,呢部分要 Imarflex 同物流商 / 報關行確認,我哋按結果落 config。 |
| **客服 / 退換流程** | 澳門客戶退換點處理(寄返香港?澳門 partner 收?),需要 ops 層面 align。 |
| **支付方式** | 除咗信用卡 / Airwallex,可能要加澳門本地支付(MPay、澳門通)—— 視乎客戶比例。 |
| **法律 / 條款** | 澳門條款 / 退換政策 / 私隱條款分開草擬。 |

### 而家報價可以做嘅 commitment

- **架構預留 multi-region / multi-currency** —— 包喺而家 build,唔額外收費。將來 activate 唔使重寫底層。
- **澳門擴展正式開展時** —— 我哋另出 Phase 2 報價,範圍會具體列(預期係 2–4 週嘅 add-on work,視乎物流 / 稅 / 支付決定咗幾多)。
- **試水溫 option** —— 如果 Imarflex 想先細規模試,可以做個輕量版:同一個香港網站,加「澳門客戶請聯絡 WhatsApp 落單」入口,人手處理首批訂單,儲返數據再決定值唔值得做正式 Phase 2。

> 一句講清:**而家先打好「將來易擴展」嘅底**(包),**真係去澳門嗰陣再正式 build**(另議)。Imarflex 唔使而家就 commit 一個完整 multi-region 功能,但亦唔會喺一年後發現「要由零改架構」。
